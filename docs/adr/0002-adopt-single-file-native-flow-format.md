# ADR-0002: Adopt a single-file native flow format

- Status: Accepted — amended in part by ADR-0009 (voice step types and
  `barge_in`) and ADR-0010 (the format must not name a TTS engine)
- Date: 2026-07-18
- Deciders: Mojolab (Arjun Venkatraman)
- Related issues: T4, T5
- Related ADRs: ADR-0003, ADR-0004, ADR-0009, ADR-0010

> **Amendment note (2026-07):** the step vocabulary and `say:`/`audio:` prompt
> model below stand, but two details are superseded. ADR-0009 adds a `listen`
> step type, per-step `barge_in`, and `intent`/`phrases` on `menu` options;
> ADR-0010 removes the assumption that `say:` renders through espeak/sox
> specifically. Both amend the schema *before* it freezes under #4, since T5,
> T6, T7 and T8 all depend on it.

## Context
Every call flow mojobol runs today is a Verboice Designer export: a `workflow.yml`
plus one `resource*.yml` and one `localized_resource*.yml` per prompt, all
cross-referenced by opaque GUIDs (e.g. `resource: { guid: 0a69cfd7-... }`
pointing into a same-directory file named after that GUID). `libs/mojobol.py`
loads `workflow.yml`, finds the step with `root: true`, and follows `next`
pointers through a `while` loop; `libs/mojoasteriskplayer.py`'s
`executeStep` dispatches each step by its `type` (`play`, `capture`, `menu`,
`record`, `playloop`) and resolves the GUIDs to find the prompt to play.

This format is a serialization of Verboice's internal object graph, not
something designed for humans:
- A single flow is a directory of many files (one workflow file plus two
  files per prompt), all of which must stay consistent for the flow to work.
- Steps reference prompts only by GUID; there is no readable prompt text next
  to the step that plays it, so understanding or editing a flow means
  jumping between files.
- GUIDs are generated by the Designer tool and are meaningless to a human or
  an LLM — hand-editing risks a typo that silently breaks a cross-reference
  (the engine has no schema validation, so this fails at call time).
- Authoring requires the Verboice Designer GUI, which we no longer want to
  depend on for new flows (see ADR-0004).

We want flows that a person can read top-to-bottom in one file, that an LLM
can emit directly from a conversation, and that stay compatible with the
existing step-dispatch model in `mojoasteriskplayer.py` so the engine change
is additive rather than a rewrite.

## Decision
Adopt one human- and LLM-authorable YAML file per flow (`flow.yml`) as the
native format going forward. A flow is a `name`, a `language`, and an ordered
list of `steps`. Each step has an `id`, a `type` (`play`, `capture`, `menu`,
`record`, `playloop` — the same set the engine already dispatches on), and a
`next` pointer (or, for `menu`, an `options` map of key → next step id).
Prompt content is inline on the step itself, as either:
- `say: "<text>"` — rendered on the fly via the existing espeak → sox 8kHz
  GSM TTS pipeline, or
- `audio: <filename>` — a pre-recorded audio file shipped alongside the flow.

Step-type-specific fields (`min_length`/`max_length`/`finish_on_key`/
`valid_values`/`attempts`/`store` for `capture`; `options` for `menu`;
`stop_key`/`max_seconds`/`store` for `record`) map directly onto the fields
`executeStep` already reads from Verboice steps today, just without the
GUID indirection.

## Consequences
### Positive
- One file per flow: the whole call flow, including every prompt's actual
  wording, is readable top to bottom without cross-referencing other files.
- Directly authorable by hand or by an LLM (see ADR-0004) — no Designer GUI
  round-trip required.
- Same step-type vocabulary as today, so the runtime change is a new loader
  (T5) rather than a rewrite of `executeStep`'s dispatch logic.
- Removes an entire class of bugs: mismatched or mistyped GUIDs between
  `workflow.yml` and its `resource*.yml` files.

### Negative / Trade-offs
- A new format needs its own schema and documentation (T4) and its own
  loader in the engine (T5); until both land, native flows can't run.
- Existing Verboice exports don't disappear — they need a conversion path
  (handled separately, see ADR-0003) or they become dead weight.
- Inline `say:` text coupled with `language` puts the burden of managing
  multiple languages within a single flow file, versus Verboice's separate
  `localized_resource` files per language; multi-language flows need a
  documented convention (tracked under T4).
